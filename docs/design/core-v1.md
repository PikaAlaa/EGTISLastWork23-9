# ETIS core v1 — design for the full Egyptian Threat Intelligence System

Status: **design only** (18 November 2026). No code, schema or behaviour changes
accompany this document. Branch `feat/core-design`.

ETIS today is a local phishing detector: `POST /analyze` runs decision policy
`decision-v2` over rules, the feed blacklist, the v4 URL model
(`ee0ba9f0077c1fd140aa`, `host_path`, frozen threshold `0.9870690448552604`) and
the deployed TF-IDF LightGBM text model. Core v1 adds the shared platform layer
that lets ETIS grow into a threat-intelligence system — Findings, an Indicator
store, Incidents, ATT&CK mapping and SOC console pages — so that future network,
malware and host engines plug into one model.

## 0. Constraints this design must keep

These come from `CLAUDE.md`, `README.md` and `LOCAL-IMPLEMENTATION.md` and are not
reopened anywhere below.

| Constraint | How core v1 keeps it |
| --- | --- |
| Free and local only: no cloud, paid services or hosting | SQLite by default (existing `DATABASE_URL`), loopback servers, existing React app and proxy. ATT&CK data is a one-time pinned download stored locally; nothing is fetched at runtime. |
| Verdicts, thresholds, frozen models, v4 rule and selection unchanged | Findings are produced **after** `calculate_final_risk_score` returns, from its output only. Nothing in core v1 is read by the decision policy. A parity test pins this (§9). |
| URLs are inert strings; no external analysis services | No engine, enrichment or console feature resolves, fetches or submits an indicator anywhere. Indicators are displayed non-clickable, as the scan page already does. |
| Privacy minimization of scans | Indicators derived from a user's scan are stored as SHA-256 hashes only (as `scan_requests` already does). Retention deletes scan-derived findings with `ETIS_RETENTION_DAYS`. |
| Generated/translated text never presented as real Egyptian SMS | Test fixtures for findings and incidents are labelled invented; no evaluation claim is made. Genuine Egyptian SMS final-test count remains 0. |
| Original September data/model/tokenizer, reviewed reports, `evaluation/targets.json`, frozen splits | Not touched. Core v1 adds tables and modules only. |
| Isolated test databases; secrets and runtime DBs out of Git | Tests use the existing in-memory SQLite fixture in `backend/tests/conftest.py`. The ATT&CK JSON is kept out of Git (§4.1). |
| No sealed final test; v4 evaluation not rerun | No evaluation step is part of this plan. |
| Feed blacklist behaviour unchanged | `blacklist_entries`, `feed_observations`, `feed_snapshots`, `feed_updates` remain the source of truth for lookups, expiry and rollback (§2). |

Out of scope for v1 (unchanged deferrals from the README): user accounts,
public community reporting, Telegram, public deployment/TLS.

## 1. Finding schema (`finding-v1`)

A **Finding** is one engine's statement that something it observed is
security-relevant. Every engine — the existing phishing flow and every future
engine — emits the same shape. A Finding is evidence, not a verdict: the
`/analyze` verdict stays where it is today, and a Finding records it.

### 1.1 Fields

| Field | Type | Notes |
| --- | --- | --- |
| `id` | UUID4 string | Generated by the emitter. |
| `schema_version` | `"finding-v1"` | Rejected if unknown. |
| `engine` | object `{name, version}` | `name` from the engine registry (§8), e.g. `phishing.analyze`; `version` pins behaviour, e.g. `decision-v2+url:ee0ba9f0077c1fd140aa+text:<model id>`. |
| `domain` | enum `phishing \| malware \| network \| host` | Fixed list; adding a value is a schema change. |
| `kind` | string code | Engine-defined, stable, e.g. `sms_phishing`, `url_phishing`. |
| `severity` | enum `info \| low \| medium \| high \| critical` | Engine-defined mapping, documented per engine (§5.2 for phishing). |
| `confidence` | enum `confirmed \| corroborated \| single_signal \| undetermined` | **Categorical, never a percentage.** ETIS scores are indicator strengths, not calibrated probabilities (README, decision-v2), so a numeric "confidence" would mislead. Derivation rules are per engine (§5.2). |
| `indicators` | list of Indicator refs (§1.2) | May be empty (e.g. a text-only finding with no extractable indicator). |
| `attack` | list of `{technique_id, matrix, attack_version, basis}` | `matrix` ∈ `enterprise \| mobile`. Validated against the local ATT&CK catalogue (§4). `basis` names the rule that produced it. |
| `evidence` | object `{reasons: [code], details: {...}}` | `reasons` are existing reason codes (e.g. `blacklist_exact`, `text_high_corroborated`). `details` holds engine-specific, **non-content** values: version ids, indicator strengths, thresholds, policy names. Never raw message text or matched snippets (privacy migration 002 removed those for a reason). |
| `observed_at` | ISO-8601 UTC | When the engine observed the activity. |
| `created_at` | ISO-8601 UTC | When stored. |
| `source` | object `{kind, ref}` | `kind` ∈ `scan \| feed \| analyst \| community \| sensor \| import`; `ref` is a local id such as `scan_requests:123` or `feed:openphish`. |
| `incident_id` | int or null | Set by correlation (§3), not by the engine. |

### 1.2 Indicator references inside a Finding

```json
{"type": "url", "value_hash": "<sha256 hex>", "value": null, "role": "delivery_link"}
```

- `type` ∈ `domain | url | ip | hash | phone | email`. For `hash`, add
  `hash_algo` ∈ `sha256 | sha1 | md5`; the hash value itself is the indicator.
- `value_hash` = SHA-256 of the **normalized** value (§2.2). For `url` this is
  exactly the existing `blacklist_entries.url_hash` formula (SHA-256 of
  `parse_url(...).canonical`), so feed and scan indicators join without
  re-hashing the feed.
- `value` is the normalized plaintext and is **null for scan-derived
  indicators**. It is filled only when the indicator already exists in the store
  with a plaintext value from a public feed, an analyst or a sensor (§2.3).
- `role` is a free engine code (`delivery_link`, `contact_phone`, `sender`,
  `lookalike_domain`, `c2`, …).

  "domain": "phishing",

  "severity": "high",
  "confidence": "corroborated",
  "indicators": [
    {"type": "url", "value_hash": "…", "value": null, "role": "delivery_link"},

  ],
  "attack": [
    {"technique_id": "T1660", "matrix": "mobile", "attack_version": "20.0", "basis": "sms_text_present"},
    {"technique_id": "T1566", "matrix": "enterprise", "attack_version": "20.0", "basis": "phishing_message"},
    {"technique_id": "T1684.001", "matrix": "enterprise", "attack_version": "20.0", "basis": "brand_decisive"}

### 1.4 Implementation shape

A Pydantic model `app/core/findings.py::Finding` (strict, `extra='forbid'`) is
the single contract. Engines return `list[Finding]`; a single
`app/services/findings.py::record_findings(db, findings)` persists them, upserts
indicators (§2), validates ATT&CK ids (§4) and runs correlation (§3). Engines
never write finding tables directly.

## 2. Indicator (IOC) store

### 2.1 Principle: a projection, not a replacement

The existing feed path is load-bearing for `/analyze`:
`calculate_blacklist_reputation_score` reads `blacklist_entries` (exact
`url_hash`, then domain count with the shared-hosting exception);
`blacklist_health` reads `blacklist_entries` and `feed_snapshots`;
`services/feeds.py` activates, expires (`EXPIRY_DAYS` 30/7/90) and rolls back
per source via `feed_observations`. **None of that changes.** The indicator
store is a read-side projection of those tables plus scan, analyst and future
sensor sightings. In v1 the `/analyze` decision path does not read the indicator
store at all.

### 2.2 Normalization

| Type | Normalized value |
| --- | --- |
| `url` | `parse_url(v).canonical` (the existing canonical identity; userinfo kept separately as today). |
| `domain` | Lower-case IDNA ASCII host, no trailing dot. The registered domain (via the pinned Public Suffix List already used in evaluation) is stored alongside as `registered_domain` for correlation. |
| `ip` | `ipaddress.ip_address(v).compressed`. |
| `hash` | Lower-case hex; length must match `hash_algo`. |
| `phone` | E.164 (`+20…` for Egyptian national numbers); short codes kept as digits with a `short_code` flag. |
| `email` | Lower-case address; IDNA domain part. |

`value_hash = sha256(normalized)`, unique together with `type`. Unkeyed SHA-256
of low-entropy values (domains, phones) is **pseudonymization, not
anonymization**; this matches the existing `scan_requests` hashes and is stated
in the console's privacy note. A keyed HMAC was rejected because it would not
join with the existing unkeyed `blacklist_entries.url_hash`, and changing that
column would change feed behaviour.

### 2.3 Plaintext rules

- Feed (PhishTank/OpenPhish/manual), analyst and sensor indicators: plaintext
  stored; these are already public or deliberately entered.
- Scan-derived indicators: hash only. If the same hash already exists with
  plaintext from a feed, the finding links to that row and the console shows the
  feed value. A user's unique, unmatched link or phone number is never stored in
  plaintext.
- The existing `/threats` decision to hide raw feed URLs in bulk remains. The
  Indicator search page shows a URL only on an exact single-indicator lookup,
  as inert text.

### 2.4 Feed merge

A function `sync_feed_indicators(db)` is run by the existing intelligence worker
(`data/scripts/manage_intelligence.py`) **after** each refresh, expiry or
rollback has committed, in its own transaction. It is idempotent:

1. For each `blacklist_entries` row: upsert a `url` indicator (`value_hash` =
   `url_hash`) and a `domain` indicator; upsert a sighting per
   `(indicator, source)` with `first_seen`/`last_seen`/`active` copied from the
   entry and `feed_observations`.
2. Mark sightings inactive when their entry became inactive. Never delete feed
   rows, never write to feed tables.

If the sync fails, the feed state and `/analyze` are unaffected; the console
shows the projection's last sync time and a `stale` badge. A parity test (§9)
asserts that every active blacklist entry has an active `url` sighting with the
same source and dates.

### 2.5 Community reports

`community_reports` (`pending | confirmed | rejected`, raw `reported_value`) has
no router today and public reporting is deferred. v1 adds no submission
endpoint. If rows exist, the console lists them for analyst review:

- **Confirm** creates an indicator sighting with `source.kind = community` and
  sets `status`/`reviewed_at`. It does **not** insert into `blacklist_entries`.
- Promoting to the blacklist (`source='manual'`) stays a separate, explicit
  analyst action, because it changes `/analyze` verdicts; it is listed as a
  later item, not part of v1 delivery.

## 3. Incidents and campaigns

### 3.1 Correlation key

Two findings are related when they share a **pivotable indicator**:
`url`, `ip`, `hash`, `phone`, `email`, or `domain` by `registered_domain`.

Excluded from pivoting (they would merge unrelated activity):

- hosts in `SHARED_HOSTING_DOMAINS` (`blacklist_lookup.py`) and their subdomains;
- verified brand domains in `brand_domains` (an official domain is a victim
  brand, not adversary infrastructure);
- an editable `correlation_stoplist` for further shared services and short-link
  providers.

### 3.2 Grouping algorithm (deterministic)

On each recorded finding with at least one pivotable indicator:

1. Find incidents in status `open` or `investigating` with an indicator overlap
   whose `last_activity_at` is within `ETIS_CORRELATION_WINDOW_DAYS` (default 14).
2. None found: create an incident only if the finding's severity is `medium` or
   above; lower findings stay unassigned but searchable.
3. One found: attach the finding; add new indicators to the incident.
4. Several found: attach to the **oldest**; record `related` links to the others.
   Incidents are never merged automatically; merging is an analyst action.
5. A matching finding for a `resolved` incident creates a new incident with
   `reopened_from` set; resolved incidents are never silently reopened.

Incident title and severity: severity is the maximum of its findings; the title
is generated from `kind` plus the matched brand (if any).

### 3.3 Campaigns

A **campaign** groups incidents that are the same operation (for example several
lookalike domains impersonating one Egyptian bank with the same contact number).
Campaigns are **analyst-created**. The console *suggests* candidates when
incidents share a `matched_brand` plus any pivotable indicator outside the
window, or share a phone/email indicator; suggestions never auto-assign.

### 3.4 Status workflow

```
open ──► investigating ──► resolved
  └───────────────────────────▲
resolved ──(reopen, note required)──► open
```

- `resolved` requires `resolution` ∈ `true_positive | false_positive | benign | duplicate`.
- Every transition writes an `incident_events` row (`actor`, `from`, `to`,
  `note`, `at`). Without accounts, `actor` is the fixed string `local-operator`.
- Incident status and resolution are **never read by the decision policy**.
  A `false_positive` resolution is evidence for the team's later review; it does
  not retune thresholds (README: any threshold change needs a new dated rule).

## 4. ATT&CK mapping

### 4.1 Local data

- Source: MITRE `attack-stix-data` collections, **pinned to version 20.0**
  (modified 2026-10-13). 20.1 (2026-11-05) is excluded because it is newer than
  two weeks at the time of design.
- Files and SHA-256 (downloaded once for this design, 2026-11-18, to a scratch
  directory and verified; not committed):

  | Collection | File | Size | SHA-256 |
  | --- | --- | --- | --- |
  | Enterprise | `enterprise-attack-20.0.json` | 55,271,014 B | `2339A3C36353D5EE2C07E98AF3FAFBF00761E0E3979EDE06402657445B7B4278` |
  | Mobile | `mobile-attack-20.0.json` | 6,095,145 B | `C7D6C923C1F8462AB1C5DB0195D81E2585DB9949D574128391C682F229C6695A` |

- Storage: `data/external/attack/` (added to `.gitignore`, like
  `data/external/phreshphish/`). Committed: `data/attack-lock.json` (collection,
  version, URL, size, SHA-256) and `data/scripts/fetch_attack.py`, which
  downloads only these two pinned files from `raw.githubusercontent.com/mitre-attack/`,
  verifies the hashes and refuses on mismatch. This is a reference-data download,
  run manually; it never sends ETIS data anywhere and is never run by the app.
- `docs/data-licences.md` gets an `attack` entry citing the MITRE ATT&CK Terms of
  Use (copyright notice required when reproducing) before any ATT&CK text is
  shown in the console.
- `scripts/initialize.py` loads a compact catalogue into `attack_techniques`
  (§7) from the local files if present. If they are absent the platform runs;
  findings keep their technique ids and the ATT&CK view shows "catalogue not
  installed".

### 4.2 Validation rules

- Only `attack-pattern` objects that are neither `revoked` nor
  `x_mitre_deprecated` are valid targets.
- Ids are stored with their matrix and the catalogue version. Upgrading ATT&CK is
  a dated change with a new lock file; existing findings keep their recorded
  version.
- `record_findings` rejects unknown, revoked or deprecated ids (fail closed on
  the mapping, not on the scan: the finding is stored without that technique and
  an `attack_mapping_rejected` reason is logged without input values).

### 4.3 SMS phishing: what the data actually says

Checked in the v20.0 files:

| Id | Matrix | Name | Tactic | Relevance |
| --- | --- | --- | --- | --- |
| `T1566.004` | Enterprise | **Spearphishing Voice** | initial-access | Voice calls, **not SMS**. Must not be used for SMS. |
| `T1566.002` | Enterprise | Spearphishing Link | initial-access | Defined in terms of spearphishing *emails*. Not used for SMS. |
| `T1566.003` | Enterprise | Spearphishing via Service | initial-access | Third-party services such as social media; not carrier SMS. Not used. |
| `T1566` | Enterprise | Phishing | initial-access | Parent, channel-neutral ("phishing messages"). Used as the Enterprise counterpart. |
| `T1660` | **Mobile** | **Phishing** | initial-access | Android/iOS; description explicitly covers social engineering in text messages. **Primary technique for SMS phishing.** |
| `T1598` / `T1598.003` | Enterprise | Phishing for Information / Spearphishing Link | reconnaissance | Messages eliciting credentials or other information. |
| `T1684.001` | Enterprise | Impersonation | stealth | New in v20. **`T1656` Impersonation is revoked** (revoked-by `T1684.001`); never emit `T1656`. |
| `T1204.001` | Enterprise | User Execution: Malicious Link | execution | The user is asked to open a link. |
| `T1583.001` | Enterprise | Acquire Infrastructure: Domains | resource-development | Lookalike domain registered by the adversary (inferred). |
| `T1476` | Mobile | Deliver Malicious Application via Other Means | initial-access | Links to an app package in SMS. ETIS has no APK detector yet; reserved for the malware engine. |

Enterprise ATT&CK v20.0 has **no SMS-specific Phishing sub-technique**; SMS
phishing is modelled by Mobile `T1660`.

### 4.4 Phishing mapping table `attack-map-v1`

A versioned, code-reviewed table keyed by existing reason codes. It runs after
the verdict and has no influence on it.

| Condition (from `/analyze` output) | Technique(s) | `basis` |
| --- | --- | --- |
| Finding emitted and `text` was submitted | Mobile `T1660` | `sms_text_present` |
| Any phishing finding | Enterprise `T1566` | `phishing_message` |
| URL-only submission | Enterprise `T1566` only; **no** `T1660` (channel unknown) | `phishing_message` |
| `checked_links` non-empty with any URL-side reason | Enterprise `T1204.001` | `link_action_requested` |
| `has_secret_request` true (`secret_request` signal) | Enterprise `T1598`; plus `T1598.003` when a link is present | `secret_request` |
| Brand technique decisive (`userinfo_brand`, `homoglyph_confusable`, `domain_embedding`, `brand_label_reuse`) or `brand_claim_from_mobile_number` | Enterprise `T1684.001` | `brand_decisive` / `brand_claim_sender` |
| Brand technique `homoglyph_confusable`, `domain_embedding` or `brand_label_reuse` | Enterprise `T1583.001` | `lookalike_domain_inferred` |

`secret_request` is not currently a field in the `/analyze` result; the emitter
recomputes `has_secret_request(text)` from the same function used by the policy
(pure function, same input) rather than changing the policy's return shape.

## 5. `/analyze` emits Findings without changing any verdict

### 5.1 Where

In `routers/analyze.py`, after `calculate_final_risk_score` returns and inside
the existing `try` that saves the scan:

```
result = calculate_final_risk_score(...)          # unchanged
try:
    save ScanRequest / ScanResult                  # unchanged
    findings = phishing_findings(result, payload, scan.id)   # new, pure
    record_findings(db, findings)                  # new
    db.commit()
except: ...                                        # unchanged handling
```

- `phishing_findings` is a **pure function** of `(result, payload, scan_id)`. It
  never calls an engine, model or threshold.
- `result` is returned to the client unmodified. `AnalyzeResponse` gains no field
  in v1 (adding `finding_ids` later is an API-contract change for `docs/api-v2.md`).
- Failure to record findings follows the existing pattern: rollback, generic log
  `scan_persistence_failed`, `saved=false`; the verdict is still returned.
  Because findings and the scan share a transaction, a scan is never saved without
  its findings or vice versa.
- Behind `ETIS_FINDINGS_ENABLED` (default on after the parity test passes); off
  reproduces today's behaviour exactly.

### 5.2 Mapping rules (`phishing.analyze`)

| `/analyze` verdict | Finding emitted | `severity` | `confidence` |
| --- | --- | --- | --- |
| `HIGH` with `blacklist_exact` | yes | `high` | `confirmed` |
| `HIGH` (other decisive reason) | yes | `high` | `corroborated` |
| `MEDIUM` | yes | `medium` | `single_signal` |
| `INCOMPLETE` with any supporting/decisive signal | yes | `medium` | `undetermined` |
| `INCOMPLETE` without signals, or `LOW` | **no** | — | — |

- `kind`: `sms_phishing` when text was submitted, `url_phishing` when URL only.
- Indicators: one `url` and one `domain` per entry in `checked_links` (hash
  only, §2.3). Phones and emails in text are extracted by a new pure helper
  using the same patterns as `has_phone_or_short_link_with_urgent_action`, hashed.
- `evidence.reasons` = `[decisive_reason] + supporting_signals`; `details` carries
  `verdict`, `policy_version`, `final_score` labelled `indicator_strength`, the
  text model version, URL-model probability/threshold per link (already returned
  to the client), and `checks_unavailable`. No raw text, URL or snippet.
- No new severity cut-offs: severity is a pure relabelling of the existing verdict.

## 6. SOC console pages (existing React app)

Added as tabs in `App.tsx` next to `scan`, `threats`, `stats`, using the same MUI
components, i18n (Arabic and English keys in `ar.json`/`en.json`), RTL cache and
non-clickable destination display. The proxy in `etis-frontend/server.mjs`
currently allows exact `/api/*` paths and only proxies through its fixed list;
it gains explicit entries for the new routes (and `PATCH` for status changes),
keeping Host/Origin, session-cookie and rate checks.

| Page | Path | Backend | Content |
| --- | --- | --- | --- |
| Incidents | `/incidents` | `GET /incidents`, `GET /incidents/{id}`, `PATCH /incidents/{id}` (status, resolution, note), `POST /incidents/{id}/merge`, campaign endpoints | Filterable list (status, severity, domain, brand, date); detail with findings timeline, indicators, ATT&CK techniques, events log and status actions. |
| Indicator search | `/indicators` | `GET /indicators?type=&q=` (exact lookup by normalized value → hash), `GET /indicators/{id}` | Sightings by source with dates and active flag; linked findings and incidents. Exact lookup only — no substring search over hashed values, no bulk URL export. |
| ATT&CK view | `/attack` | `GET /attack/techniques?matrix=` , `GET /attack/coverage` | Tactic × technique grid for Enterprise and Mobile v20.0, coloured by count of findings in a date range; technique detail with name, MITRE link (inert text) and linked incidents; "catalogue not installed" state. Shows the ATT&CK copyright notice. |
| Community review (optional) | inside Indicators | `GET /community-reports`, `PATCH /community-reports/{id}` | Only if rows exist; confirm/reject per §2.5. |

All new endpoints use `verify_api_key` like the existing routers, bind to
loopback, and return `database_unavailable` on errors without echoing values.

### 7.2 Migrations

Existing chain: `001_baseline → 002_private_scans → 003_feed_observations`.
Caveat: `001_baseline` creates every table currently in `Base.metadata`
(except four named ones), so once the new models are imported by `app.models`, a
fresh database gets them from 001 before 004–006 run. Plan: 004–006 define
their tables explicitly with `op.create_table` (not from live models) and skip
a table that already exists with the expected columns; the migration tests
cover both the fresh path (created by 001) and the upgrade path (created by
004–006) and compare the resulting schemas.

| Revision | Content | Downgrade |
| --- | --- | --- |
| `004_indicators` | `indicators`, `indicator_sightings`, `correlation_stoplist`. Data step: none (sync is a runtime job, so migration time stays bounded and the feed tables are untouched). | Drop the three tables (projection is rebuildable). |

Each migration is tested from empty schema, from a database at `003` with
legacy rows, and for idempotent re-run, matching the existing
`test_data_and_migrations.py` style. PostgreSQL compatibility follows the
existing SQLite/PostgreSQL code paths; Docker/PostgreSQL execution remains
unverified locally, as recorded today.

Retention: `data/scripts/retention.py` gains deletion of scan-derived findings
older than `ETIS_RETENTION_DAYS` (via the `scan_request_id` cascade), and of
scan-only indicators no longer referenced. Incidents remain with their events;
their counts stay, their deleted findings are shown as "expired by retention".

## 8. Future engines (network, malware, host)

### 8.1 Contract

```python
class Engine(Protocol):
    name: str            # e.g. "network.zeek_conn", "malware.yara", "host.sysmon"
    version: str
    domain: Literal['phishing', 'malware', 'network', 'host']
    def analyze(self, observation: Observation) -> list[Finding]: ...
```

- Registered in a new `app/engines/registry.py` (distinct from the existing
  brand-registry module `app/services/registry.py`) with a health check, so `/health/ready` reports per-engine availability the same way
  it reports blacklist and text model today. A missing engine degrades honestly;
  it never masks another engine's result.
- Engines only return Findings; `record_findings` does persistence, indicator
  upsert, ATT&CK validation and correlation. Each engine ships its own versioned
  ATT&CK mapping table and severity/confidence rules in its module docstring and
  tests.
- Inputs are **local files or local sensors only**: e.g. Zeek/Suricata logs from
  the operator's own network, YARA rules run over files the operator supplies,
  Sysmon/Windows event exports. All are free/open source tools run locally. No
  cloud sandbox, VirusTotal or similar lookup.

### 8.2 Sketches

| Engine | Input | Example kinds | Indicators | ATT&CK (to be verified against the catalogue when built) |
| --- | --- | --- | --- | --- |
| `network.*` | Zeek/Suricata logs (import) | `known_bad_destination`, `beaconing` | `ip`, `domain`, `url` | per-rule, e.g. Command and Control techniques |
| `malware.*` | Operator-supplied files, YARA | `yara_match`, `known_bad_hash` | `hash`, plus embedded `url`/`domain` | per-rule; Mobile `T1476` for APK-in-SMS links once an APK detector exists |
| `host.*` | Sysmon/EVTX exports | `suspicious_process`, `persistence` | `hash`, `ip`, `domain` | per Sigma rule tag |

Network and host findings will match the feed indicators automatically through
the shared `domain`/`url`/`ip` hashes, which is the main payoff of §2. Malware
samples are never executed by ETIS.

## 9. Test plan

All tests use the existing isolated in-memory SQLite fixture; no network access
(the ATT&CK catalogue tests use a small committed fixture subset extracted from
v20.0 with its source hash recorded, or skip with a clear reason when the
fixture is absent).

1. **Verdict parity (gate).** For every existing case in the replay/probe
   suites and endpoint tests, the `/analyze` response is byte-identical (except
   `timing_ms`) with `ETIS_FINDINGS_ENABLED` on and off. Policy version, decisive
   reason, signals and thresholds are asserted unchanged.
2. **Finding schema.** Valid/invalid examples; enum rejection; `extra='forbid'`;
   no raw text or URL in any persisted column (marker-string test, like the
   existing privacy test, over `findings`, `indicators`, `evidence` and logs).
3. **Phishing mapping.** Table-driven tests for §5.2 (each verdict/reason row)
   and §4.4 (each basis), including: URL-only produces no `T1660`; `T1656` and
   `T1566.004` are never emitted for SMS.
4. **Normalization.** URL hash equals `blacklist_entries.url_hash` for the same
   canonical URL; IDNA, IPv6 compression, E.164 Egyptian numbers, hash length.
5. **Feed projection parity.** After activate, expire and rollback (existing
   feed test scenarios), `sync_feed_indicators` gives one active sighting per
   active entry/source and inactive otherwise; running it twice is a no-op;
   feed tables are byte-identical before and after sync.
6. **Correlation.** Shared URL → same incident; shared shared-hosting or
   official brand domain → separate incidents; multiple matches → oldest +
   `related`; resolved incident + new finding → new incident with
   `reopened_from`; window boundary; low-severity finding without incident.
7. **Workflow.** Allowed and forbidden transitions; `resolution` required;
   events written; reopen requires note.
8. **ATT&CK catalogue.** Loader skips revoked/deprecated; unknown id rejected
   and logged without values; lock-file hash mismatch refuses to load.
9. **Migrations.** Empty → head; `003` with legacy data → head; re-run; downgrades
   as specified; existing tables' schemas unchanged (compared column by column).
10. **Retention.** Scan-derived findings and orphan scan-only indicators deleted;
    incidents and events kept.
11. **API and proxy.** Auth required; validation errors do not echo input; proxy
    rejects unlisted paths; Host/Origin checks still apply.
12. **Frontend.** Build and oxlint pass; Arabic/English strings present for every
    new key; RTL layout; 390-pixel viewport without horizontal overflow (manual
    check as recorded today).

Per CLAUDE.md, every implementation commit runs pytest, database
initialization, frontend build and lint. No sealed final test is run.
